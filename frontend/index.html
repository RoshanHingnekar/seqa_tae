ESTIMATION METHODOLOGY & VIVA GUIDE

ACADEMIC & INDUSTRY SPECIFICATION
⚠️
IMPORTANT ASSUMPTION:

“This estimator provides an approximation based on configurable assumptions. Actual QA effort depends on requirements quality, application complexity, automation level, test environment stability, team experience, tooling, defect density, regression scope, and other project-specific factors.”

01. What is Lines of Code (LOC)?

Lines of Code (LOC) measures the physical size of the software codebase. In testing estimation, LOC represents the scope of logic and surface area that could harbor defects. While not a direct proxy for test count, larger codebases incur structural exploration and comprehension overhead.

02. What are Test Cases?

A Test Case is a documented set of preconditions, inputs, execution procedures, and expected outcomes designed to verify a specific software requirement or code branch.

03. What is Test Coverage?

Test Coverage (%) represents the proportion of requirements, code paths, or features exercised by the test suite. Higher coverage diminishes untested code risks but demands non-linearly increasing effort.

04. Why does higher coverage require more effort?

Achieving baseline coverage (60-80%) covers the primary "happy paths". Reaching 90-100% requires designing complex scenarios, boundary value tests, concurrency races, error-handling injection, and mock fixtures, leading to exponentially diminishing returns per hour invested.

05. What is QA Productivity?

QA Productivity is the rate of test execution throughput, measured here in test cases completed per hour (e.g., 5 to 8 cases/hr for manual regression). It defines the team's operational velocity.

06. What is Project Complexity?

Architectural complexity accounts for integrations, distributed microservices, multi-tier security, statefulness, and data volume.
• Low (0.85): Simple CRUD, minimal integrations.
• Medium (1.00): Standard enterprise web application.
• High (1.25): High concurrency, financial transactions, multi-tenant compliance.

07. What is Regression / Retest Effort?

When bugs are resolved by developers, QA must retest the defect and perform regression testing to ensure fixes did not corrupt untouched features. A standard 15% to 25% buffer protects against cycle slippage.

08. What is a Person-Hour and Person-Day?

A Person-Hour is the productive labor accomplished by one engineer in 60 minutes. A Person-Day is standard working hours (typically 8.0 hours) of continuous engineering effort: person_days = total_hours / working_hours_per_day.

09. What is Full-Time Equivalent (FTE)?

FTE converts total effort hours into the equivalent number of full-time dedicated employees over a standard business month (assuming 20 workdays × 8 hours = 160 productive hours): fte = total_hours / 160.0.

📐 FORMULAIC SPECIFICATION MATRIX

1. Test Execution Hours = (Test Cases × Avg Test Minutes) / 60
2. Coverage Factor = Target Coverage (%) / 80.0
3. LOC Testing Hours = LOC × LOC_TESTING_FACTOR (configurable, default 0.0)
4. Base QA Effort = (Test Execution Hours + LOC Testing Hours) × Coverage Factor × Complexity Factor
5. Retest Overhead = Base QA Effort × (Retest Buffer % / 100)
6. Total QA Effort = Base QA Effort + Retest Overhead
7. Person Days = Total QA Effort / Working Hours Per Day
8. QA FTE = Total QA Effort / 160.0
9. Duration Days = ⌈Total QA Effort / Working Hours Per Day⌉
